# Appins Test and Regression Engineering

## Principle
Test externally observable behavior and invariants. A test is evidence only for the code path and environment it actually exercises.

## Workflow
1. Read workspace scripts, test conventions, fixtures, app construction, and test setup before adding a framework or dependency.
2. Define the invariant and expected failure before writing code. For bug fixes, create a test that fails on the old behavior where practical.
3. Select the smallest suitable layer:
   - unit test for deterministic domain logic;
   - Fastify injection/API test for routes, status codes, headers, and error contracts;
   - PostgreSQL integration test for constraints, transactions, migrations, and query behavior;
   - web component test for user-visible states and accessibility;
   - end-to-end/live-provider test only when its external environment and credentials are authorized and available.
4. Include success, invalid input, unauthorized actor, missing resource, boundary values, dependency failure, timeout, and retry/idempotency cases as applicable.
5. Avoid flaky tests: no real sleeps when controllable clocks or synchronization are possible; isolate database state; avoid order dependence; use deterministic fixtures and bounded timeouts.
6. Assert meaningful outcomes, not implementation trivia. Do not mock the very control being tested. For security tests, demonstrate the denial path and verify no side effect occurred.
7. Run targeted tests first; then typecheck/build/full workspace tests as feasible. Record exact commands and exit outcomes. Do not describe skipped tests as passed.
8. Review whether the test would catch the original regression; mention any coverage gaps.

## Appins priority scenarios
- Session creation, expiry, logout/revocation and invalid configuration.
- CSRF behavior for matching, mismatching, and missing Origin/Referer where relevant.
- Owner scoping/IDOR across all data-access paths.
- Rate-limit threshold, key isolation, cleanup/memory bounds, and documented multi-replica limitations.
- Encryption-key absence/rotation and ensuring secrets never appear in logs or API responses.
- PostgreSQL TLS verification modes and invalid certificates/hostnames in a controlled test setup.
- Webhook signature mismatch, malformed payload, replay/duplicate delivery, and idempotency.
- Migration repeatability, lock contention, transaction rollback, and schema constraints.
- Provider timeouts, non-success responses, malformed payloads, and safe retry policy.
- UI states distinguish zero, unavailable, stale, loading, and error; do not silently render fabricated metrics.

## Output
Summarize scenarios, new/changed tests, commands run, outcomes, and tests that could not be run. Never claim coverage percentages unless generated by a coverage tool and tied to a specific command.
